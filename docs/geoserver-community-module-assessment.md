# Publishing the S-57 ENC plugin as a GeoServer community module

**Decision report · 24 November 2026 · Plugin 0.4.0 at `ddf16f6`**

**Open a discussion with GeoServer Developers now. Aim first for an ordinary community module on the development branch.** The plugin already answers a question GeoServer users have asked about publishing a usable nautical chart from S-57 cells. Making the vector features readable solves only part of that problem. The distinctive contribution is the combination of chart updates, scale-aware selection across overlapping cells, and reusable portrayal through WMS and WMTS. The best first milestone is a developer outside this project installing a matching nightly ZIP and rendering one updated cell. [Original GeoServer user discussion](https://discourse.osgeo.org/t/geoserver-users-s-57-support/43740) · [Plugin source at assessment](https://github.com/AShapira/geoserver-enc-plugin/tree/ddf16f65e75bbd17baf8ebbd34d0a61e7ddc9022)

**One Project Steering Committee (PSC) member can approve entry.** The work ahead is establishing who will maintain the submission, documenting the rights to imported portrayal material, and making the plugin build, install and test inside GeoServer. If your goal is a ZIP that matches an official GeoServer release, plan for the **pending** tier. It gives the project a way to distribute the module with a release while collecting production feedback. [Developer policy](https://docs.geoserver.org/main/en/developer/policies/community-modules/) · [User-facing distribution policy](https://docs.geoserver.org/main/en/user/community/)

## What each publication route gives users

| Status | What users receive | Decision and continuing obligations |
| --- | --- | --- |
| Independent plugin, as today | Your own release schedule and packaging. The v0.4.0 GitHub release lists an air-gap build ZIP and checksum as uploaded assets. | You select and validate each GeoServer target, host downloads, handle user reports and explain compatibility. The current standalone POM targets 3.0.2 and 2.28.0. |
| Ordinary community module | Upstream source and, once configured for packaging, an experimental ZIP alongside branch nightlies. A nightly may be incompatible even with a numbered release from the same series. An exact build for an existing release requires the matching tagged sources and compatible module sources. | Explain its public value and obtain one PSC member’s approval. Arrange contributor paperwork and scoped access. The creation policy sets no numerical coverage threshold. Users receive community code as-is. |
| Pending community module | A matching ZIP in the release’s **community** folder. Users gain a reproducible install as the module seeks more deployment experience. | One PSC member approves the move. Show general applicability, an active maintainer, passing tests and QA, at least **30%** maintained test coverage, GPL-compatible content, a signed contributor agreement and a user-manual page identifying the outstanding work. Set module status to `PENDING`, add contact and remaining work, enable the `pending` build profile and update the applicable website download listings. |
| Official optional extension | A GeoServer-versioned extension ZIP with the supported release. This is the natural long-term destination for optional chart functionality. | Submit a GeoServer Improvement Proposal (GSIP). A majority of the PSC must consider the module stable. General applicability, an active maintainer, passing QA, at least **60%** maintained coverage, cleared IP, signed agreement and user documentation all apply. After approval, move the module to `src/extension`, migrate Maven profiles, assembly, download links and documentation. |

The pending tier is available when release-matched distribution is useful. The promotion policy also describes direct promotion of a mature community module. For a GSIP, publish the proposal on the project wiki, request feedback and follow the formal vote. The normal voting window is ten days or until all PSC members have voted, with one possible extension. That clock applies to a formal vote. The initial discussion, code review and release scheduling have no comparable delivery date. ## The path from this repository to a public nightly

1. **Start one public topic.** Post in GeoServer Developer on OSGeo Discourse, or introduce it at a GeoServer developer meeting and record the outcome on the forum. Registered forum participants can also start a topic by email at `geoserver-developer@discourse.osgeo.org`. Describe the use case, link the code, name the proposed human maintainer if they agree, and ask for a PSC member’s approval and advice on scope. The FIPS proposal is a short example of a maintainer describing a native prerequisite, test strategy and target series, then receiving a public +1. [Developer forum](https://discourse.osgeo.org/c/geoserver/developer/63) · [Communication and meetings](https://geoserver.org/devel/) · [FIPS proposal and response](https://discourse.osgeo.org/t/geoserver-fips-compliance-community-module/154844)
2. **Establish the right to contribute.** Follow the individual or corporate agreement route below. For community commit access, the developer guide asks the maintainer to identify their GitHub account, notify the developer list after completing the agreement and work from a fork. Access is limited to the module they maintain. Changes to shared build files or core behavior should be reviewed by the relevant committers. [Commit access](https://docs.geoserver.org/main/en/developer/policies/committing/) · [Review policy](https://docs.geoserver.org/main/en/developer/policies/review/)
3. **Target main and file a GEOS issue.** GeoServer asks new features to start on its development branch. Link the issue, forum decision and pull request, use the GEOS issue key in commits, include tests and respond to review. A suitable feature may be proposed for stable backport after a month on main. Evaluate the branch’s policy before promising a download for older installations. On the assessment date GeoServer listed 3.1.x as development, 3.0.2 as stable and 2.28.6 as maintenance. The plugin’s 2.28.0 validation is an earlier patch level. [Pull request policy](https://docs.geoserver.org/main/en/developer/policies/pull_request/) · [Branch policy](https://docs.geoserver.org/main/en/developer/policies/community-process/) · [Downloads by series](https://geoserver.org/download/)
4. **Integrate the module into the Maven build.** A plausible name is `src/community/s57` with artifact `org.geoserver.community:gs-s57`, subject to project agreement. Inherit the GeoServer `community` parent and its branch revision. Use the branch’s managed GeoTools, Spring and test dependencies. Preserve the GeoTools service registrations and the GeoServer Spring wiring. Add the same `s57` profile to `src/community/pom.xml` and `src/web/app/pom.xml`. Keep optional dependencies out of a default server install. [Module creation instructions](https://docs.geoserver.org/main/en/developer/policies/community-modules/) · [Example community POM](https://github.com/geoserver/geoserver/blob/main/src/community/updates-checker/pom.xml) · [ENC service registrations](https://github.com/AShapira/geoserver-enc-plugin/tree/ddf16f6/src/main/resources/META-INF)
5. **Make publication part of the build.** For current main, add the module to the aggregate `communityRelease` profile and supply a module-local `src/assembly/assembly.xml` for the `assembly` profile. The parent skips modules without this descriptor. Produce a ZIP such as `geoserver-<branch-version>-s57-plugin.zip`, with the installable JAR at its root, any genuinely missing runtime dependencies, license notices and concise installation instructions. Inspect the ZIP for duplicated GeoServer or GeoTools libraries. The current Python packager puts the JAR under `lib/` and bundles source, scripts and evidence, so its archive serves a different installation workflow. [Current assembly logic](https://github.com/geoserver/geoserver/blob/main/src/community/pom.xml) · [Working assembly example](https://github.com/geoserver/geoserver/blob/main/src/community/updates-checker/src/assembly/assembly.xml) · [Current ENC packager](https://github.com/AShapira/geoserver-enc-plugin/blob/ddf16f6/scripts/package.py)
6. **Make it findable and verify the public artifact.** Add a page under `doc/en/user/community/s57/` on main, link it in the community index and `mkdocs.yml`, and coordinate the nightly download listing. Add a `ModuleStatus` Spring bean with category `COMMUNITY`, contact and documentation link so an administrator can identify what is installed. A useful status page could also report GDAL availability. After merge, download the actual ZIP and corresponding GeoServer nightly, install on an empty data directory, open one cell, request WMS and WMTS output, restart, and check uninstall instructions. A successful local Maven build proves only part of that path. [Community manual source](https://github.com/geoserver/geoserver/blob/main/doc/en/user/community/index.md) · [Current navigation](https://github.com/geoserver/geoserver/blob/main/mkdocs.yml) · [Status bean example](https://github.com/geoserver/geoserver/blob/main/src/community/updates-checker/src/main/resources/applicationContext.xml) · [Nightly download page](https://geoserver.org/release/main/)

## What the plugin can demonstrate today

The repository records an import and integrity check of **7,114 active NOAA cells** from the 14 November 2026 catalogue. It separately records chart publication on standalone GeoServer 2.28.0 and 3.0.2, offline installation on Kartoza 2.28.0, and WMS, WFS and tile checks on GeoServer Cloud 3.0.2. These are maintainer-run deployments. An independent operator installing from upstream instructions would answer a different question about repeatability. The national catalogue demonstrates scale, while a small query and a chart image from a single cell will be easier for a reviewer to verify. Maven resolved WMS core build `20261124.014014-336` and GeoPackage build `20261123.102923-165`. This establishes compilation and fixture-backed tests against those artifacts. The full upstream Maven build, GeoServer startup, public ZIP installation and render on that branch still need verification. ## Rights and provenance to settle before the code submission

**Identify the human or organization entitled to submit the code.** The history to the assessed commit has eight commits under the author name `Codex`. Git metadata cannot establish authorship, employer rights or an agreement on file. Record the human maintainer and contact, any employer or client interests, and which portions they can contribute. The project's small single-file exception does not cover a new multi-file module. For an employee contribution, check permission, waiver or corporate authorization. The corporate form can identify designated employees and an existing body of software. The committing guide directs signed forms to `info@osgeo.org`. [GeoServer contribution rules](https://github.com/geoserver/geoserver/blob/main/CONTRIBUTING.md) · [OSGeo individual agreement](https://www.osgeo.org/wp-content/uploads/individual_contributor.pdf) · [OSGeo corporate agreement](https://www.osgeo.org/wp-content/uploads/corporate_contributor.pdf)

**Read the agreement itself when deciding what you are granting.** GeoServer’s guide uses “assignment” terminology. The linked individual form reserves the contributor’s rights subject to a perpetual non-exclusive copyright license and a defined patent grant. Sections 4, 5 and 7 cover authority, original contributions and separately identified third-party submissions. Ask OSGeo how it wants the named upstream materials recorded for this import. Permission to distribute a library and authority to grant rights as its author are separate questions. [OSGeo individual agreement, §§2–7](https://www.osgeo.org/wp-content/uploads/individual_contributor.pdf) · [GeoServer committing guide](https://docs.geoserver.org/main/en/developer/policies/committing/)

**Account for each category that will ship.** The repository declares GPL-2.0-or-later. GeoServer distributes under GPL version 2 or later with named exceptions. Preserve original grants and notices on imported material. The project’s root license and the presence of a license file in an upstream repository do not by themselves settle every asset’s origin or authorize a new exception. [GeoServer license notice](https://github.com/geoserver/geoserver/blob/main/LICENSE.md) · [Plugin licensing and provenance](https://github.com/AShapira/geoserver-enc-plugin/blob/ddf16f6/NOTICE.md)

## Engineering decisions for the first upstream review

**Define a contribution that a fresh installation can use.** Propose the read-only single-cell store, update processing and GeoPackage cache as the smallest independently demonstrable unit. Include catalogue selection, the WMS scale callback, portrayal and the minimal tools to exercise them if a maintainer can support them and the portrayal rights are clear. If the catalogue needs an externally prepared SQLite file, document its producer and supported format versions. If styled output depends on generated assets or a publisher outside GeoServer, version that dependency and give the reviewer an end-to-end example. Keep the provider downloaders, national demo, browser viewer, Kartoza recipes and air-gap kit in this repository initially. This lets those tools follow their own release schedule. The distinctive chart portrayal should still be visible in the demonstration. [Plugin architecture and installation](https://github.com/AShapira/geoserver-enc-plugin/blob/ddf16f6/README.md) · [Deployment guide](https://github.com/AShapira/geoserver-enc-plugin/blob/ddf16f6/docs/publishing-guide.md)

**Explain the relationship to GeoTools and OGR.** GeoServer already has a community OGR vector store that calls the native library through JNI. The ENC store runs the GDAL converter in a separate process, caches read-only GeoPackages and adds chart-specific behavior. Propose a GeoServer home for the integrated feature. Ask whether maintainers see value in a reusable GeoTools datastore later. A GeoTools unsupported module has a separate process and an LGPL licensing model. Moving GPL-derived portrayal into it would require its own rights analysis. [GeoServer OGR datastore](https://docs.geoserver.org/main/en/user/community/ogr-store/) · [GDAL S-57 driver](https://gdal.org/en/stable/drivers/vector/s57.html) · [GeoTools new-module process](https://docs.geotools.org/latest/developer/procedures/create.html) · [GeoTools licensing](https://docs.geotools.org/latest/userguide/faq.html)

**Settle what installing the JAR should do to a server.** On standalone GeoServer, the initializer defaults to installing 1,530 global styles and 1,236 graphics before anyone opens a chart. It checks existing names and bytes, and a conflict can interrupt initialization after earlier writes. An administrator can set `-Denc.installStyles=false`. The documented Cloud arrangement uses a single writer and shared storage. Ask upstream whether global style installation should require explicit activation. Document the disk and catalogue effects, collision recovery, upgrade, backup, tile invalidation and removal without disturbing user-owned styles. A separately installable portrayal pack would also give users of the datastore alone a smaller installation. [Startup implementation](https://github.com/AShapira/geoserver-enc-plugin/blob/ddf16f6/src/main/java/org/enc/geoserver/StyleLibraryInstaller.java) · [Style lifecycle and Cloud topology](https://github.com/AShapira/geoserver-enc-plugin/blob/ddf16f6/docs/shared-styles.md)

**Make the native runtime and trust model explicit.** GeoServer needs matching GeoPackage libraries and the service account needs GDAL’s `ogr2ogr`, S57/GPKG/SQLite drivers, dictionaries, PROJ data, source access and a writable cache. The publishing tools add Python dependencies. Report missing capabilities clearly. Native Windows server operation is unverified. The current store takes source, cache and executable paths as strings, and its factory reports itself available unconditionally. Ask reviewers how to respect workspace and system filesystem sandboxes through the UI and REST, and whether executable selection belongs in operator-level configuration. Document read-only chart mounts, cache growth and ownership, conversion timeouts, concurrent requests and invalidation when charts change. Scope Cloud support to named tested configurations. [ENC store parameters](https://github.com/AShapira/geoserver-enc-plugin/blob/ddf16f6/src/main/java/org/enc/geoserver/S57DataStoreFactory.java) · [Converter and cache](https://github.com/AShapira/geoserver-enc-plugin/blob/ddf16f6/src/main/java/org/enc/geoserver/GdalCache.java) · [Filesystem sandbox policy](https://docs.geoserver.org/latest/en/user/security/sandbox/) · [Existing GeoServer executable configuration](https://docs.geoserver.org/stable/en/user/extensions/ogr/)

**Document the chart product accurately.** Describe it as visualization and read-only feature access for unencrypted S-57 charts with experimental S-52-derived portrayal. Tell users how to identify the source edition and update, refresh data and tiles, and inspect known approximations. Make the limits visible on the manual’s first page and in the demo. The project has no claim to ECDIS type approval, navigational fitness or complete S-52 conformance. Encrypted S-63 products and S-101 are separate capabilities. Publishing under GeoServer changes software distribution, not chart permissions or certification. [Portrayal limitations](https://github.com/AShapira/geoserver-enc-plugin/blob/ddf16f6/docs/portrayal.md) · [Project format scope](https://github.com/AShapira/geoserver-enc-plugin/blob/ddf16f6/docs/future-formats.md) · [IHO on ENCs and ECDIS](https://iho.int/en/enc-ecdis)

## The maintainer’s responsibilities after publication

| When | What the maintainer owns |
| --- | --- |
| When a user reports a problem | Monitor the GeoServer forums and GEOS issue tracker. Request the exact GeoServer build, plugin build, GDAL version, chart edition and update, and a redistributable minimal example. Distinguish import, scale/portrayal, stale tile and provider-data issues. Keep chart sources private when their terms require it. |
| When upstream changes | Follow GeoServer and GeoTools API, dependency and build changes. Keep the module compiling on main, review relevant PRs and fix regressions. For fixes, assess each active branch and record whether it is affected and whether a backport is feasible. Recheck the actual download on supported combinations. |
| When a security issue is suspected | Use GeoServer’s private GitHub vulnerability reporting or `geoserver-security@lists.osgeo.org`. Coordinate investigation, fixes and disclosure with the project. Track GDAL and other dependencies, distinguishing what ships in the ZIP from what the operator installs. |
| When requesting pending or supported status | Own the manual, tests, coverage and packaging. Recruit independent testers with different producers, upgrades and real deployments. Publish remaining work and what kind of help it needs. Volunteer review has no guaranteed turnaround. A second maintainer or funding can improve continuity. |
| When time or funding runs out | Give early notice on the developer forum, identify a successor and leave reproducible build and release instructions. An inactive maintainer or a build break can remove a module from pending. A problematic unmaintained extension can be demoted after a public call for someone to take over. |

The individual contributor agreement imposes no general support obligation. Continuing to hold pending or supported status, however, depends on an active maintainer. Decide who will handle reports and broken builds before offering that commitment to users. ## Recommended sequence and decision points

| Stage | Evidence that closes the stage |
| --- | --- |
| Discuss now | A named person willing to own the proposed scope, a short public description, a link to reproducible results, and a PSC member’s recorded response. Ask specifically about the home of the datastore and the global style installation. |
| Before submitting code | Rights-holder and contributor paperwork settled, third-party inventory reviewed, scope agreed, a small fixture with usable terms, and a passing build inside the upstream main reactor. Defer any material whose distribution rights remain unresolved. |
| Before announcing availability | Reviewed GEOS issue and merged PR, green upstream build, current manual and status entry, a downloadable nightly ZIP, and an independent install/render/restart check against the matching nightly. Give users the exact download pairing. |
| When users need release-matched downloads | Request pending status with repeatable upstream coverage, a named contact, QA results and a public list of outstanding work. Good requests for help here include testing more producers, reviewing symbol provenance, and checking upgrades in existing catalogues. |
| When seeking official extension status | Bring operational history, reproducible coverage of at least 60%, remaining issue triage, maintenance capacity and the required GSIP. Offer the PSC evidence from other operators in addition to internal catalogue-scale benchmarks. |

**Suggested first forum message** — review the scope and add the real maintainer’s name before sending.

> Subject — Proposed S-57 ENC community module
>
> I’d like to propose a GeoServer community module for publishing unencrypted S-57 electronic navigational charts. It uses GDAL to apply chart updates and cache features in GeoPackages. It can select overlapping cells by scale and render day, dusk and night charts through WMS and WMTS. The portrayal is experimental and intended for visualization.
>
> The implementation and test results are in the [ENC plugin repository](https://github.com/AShapira/geoserver-enc-plugin). I’m proposing a first contribution on main, with the provider downloaders and deployment kits maintained separately. The current standalone version installs a shared style library at startup. I’d appreciate guidance on whether the portrayal pack should be opt-in and whether the datastore and GeoServer integration should initially live together.
>
> Would a PSC member be willing to approve this as a community module and advise on that scope?
